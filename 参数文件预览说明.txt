二、总览：两份参数合并后进入同一条预览路径
------------------------------------------

参数有两个来源，合并后对预览而言只剩一份“名称 -> 文本”字典：

- 文件来源：--params-file params.json，由 read_params_file
  （report.py:459-511）按 UTF-8 读取并整体校验，返回字符串字典。
- 命令行来源：可重复的 --param name=value，由 parse_param_options
  （report.py:947-967）在第一个等号处拆成名称/值。

合并由 merge_params（report.py:514-525）完成：先放入文件中的全部
条目，再用命令行条目整体覆盖，因此同名时命令行值覆盖文件值，且与两
种选项在命令行上的先后顺序无关；命令行空字符串同样覆盖文件中的非空
值。合并后的字典与直接写若干 --param 得到的字典走完全相同的下游：
main 预览分支把它作为 params 传给 preview_csv
（report.py:1198-1207），再经既有的参数校验、SQL 白名单、占位符
绑定、只读开库取数，最后向标准输出写 CSV（preview_csv，
report.py:687-711）。

预览路径不写任何报告文件：preview_csv 全程只接触标准输出
（report.py:709-710），main 的预览分支在 report.py:1207 即
return 0，导出分支末尾的“已导出 N 行数据：路径”提示
（report.py:1234）在该分支不可达。

四、预期结果一：仅用参数文件（小明，备注为空字段）
--------------------------------------------------

在同时备好 sample.sqlite、query.sql、params.json（内容
{"who":"小明"}）的目录执行：

    python report.py --db sample.sqlite --sql-file query.sql \
        --params-file params.json --preview 1

按源码推导的静态预期：

- 标准输出仅为带列名的 CSV，经 csv.reader 解析后恰为

      [["姓名", "备注"], ["小明", ""]]

  表头 姓名、备注 来自 cursor.description（经 _fetch_rows，
  report.py:614）；WHERE p.name = '小明' 只命中 id=1 一行；该行备注
  是 SQL NULL，本例未给 --null-text，默认空字符串，故 NULL 写成空
  字段（_csv_records 的 None 替换，report.py:651-653；默认值
  report.py:1107-1108）；--preview 1 只展示一行数据
  （rows[:1]，report.py:709）。物理形态按标准 csv 方言为
  UTF-8、行尾 \r\n，即形如 “姓名,备注\r\n小明,\r\n”（推导结果，
  非实测）。
- 退出码 0（预览分支 return 0，report.py:1207）。
- 标准错误为空。
- 标准输出不追加“已导出”等成功提示（report.py:1234 不可达）。
- 不创建任何报告或临时文件；源库、query.sql、params.json 均只被
  读取，字节不变。

六、选项先后顺序无关；命令行空字符串覆盖非空文件值

   {"who": "小红"}，预览都输出小红与完整备注一行：

       python report.py --db sample.sqlite --sql-file query.sql \
           --params-file params.json --param who=小红 --preview 1
       python report.py --db sample.sqlite --sql-file query.sql \
           --param who=小红 --params-file params.json --preview 1

   源码依据：merge_params 不读取命令行次序，只做“文件字典 -> 命令行
   字典 update”（report.py:522-524）。现有测试断言：
   test_cli_overrides_file_regardless_of_option_order
   （test_params_file.py:421-433）以 subTest 覆盖上述两种次序，均
   断言退出码 0 且解析结果第二行为 ["小红", NOTE_VALUE]。

2. 追加 --param who= 时，等号后的空字符串是有效文本值，同样覆盖文件

七、反例：{"who":1} 配 --param who=小红 仍被拒绝

把 params.json 内容改为（值为 JSON 数字 1，不是字符串）：

    {"who":1}

    python report.py --db sample.sqlite --sql-file query.sql \
        --params-file params.json --param who=小红 --preview 5

先整体读取并校验参数文件（report.py:1186），read_params_file 在

  report.py:506-509 的格式串（路径用 %s、参数名用 %r、类型说明来自
  _json_value_kind，数字 -> “数字”，report.py:444-456），消息逐字

      参数文件 params.json 中参数 'who' 的值必须是 JSON 字符串，收到 数字

      错误: 参数文件 params.json 中参数 'who' 的值必须是 JSON 字符串，收到 数字

八、参数文件的读取与校验规则
----------------------------

下列规则全部针对 --params-file；合并后的字典在 preview_csv 的
_prepare_statement 中还会经 validate_params 再复核一次
（report.py:560、319-337），与纯 --param 路径同一标准。

1. 编码：文件按二进制读入后以 utf-8-sig 解码（report.py:475-487），
   允许开头恰一个 BOM，BOM 被剥除，其余字节原样解码；非 UTF-8 抛
   ValueError。文件只被读取，绝不改写。现有断言：
   test_leading_bom_is_accepted（test_params_file.py:75-77，
   BOM + {"who":"小红"} 读回 {"who": "小红"}）；
   test_invalid_utf8_rejected（test_params_file.py:159-162）。
2. 内容必须恰为一个 JSON 对象：数组、数字、布尔、null、字符串等顶层
   形态一律拒绝（report.py:494-498）；空对象 {} 有效。现有断言：
   test_non_object_toplevel_rejected（test_params_file.py:101-107）、
   test_empty_object_returns_empty_dict（test_params_file.py:79-81）。
3. 值只接受 JSON 字符串：数字、布尔值、null、数组与嵌套对象一律拒绝
   （report.py:505-509）；空字符串值有效（report.py 中
   read_params_file 文档字符串 467-469）；一个非法条目会拒绝整个
   文件，即使同文件中另有合法条目。字符串经 JSON 解码后的中文、首尾
   空格、换行、等号、引号和分号原样保留。现有断言：
   test_empty_string_value_is_valid（test_params_file.py:83-85）、
   test_decoded_string_text_is_preserved
   （test_params_file.py:87-91）、
   test_one_illegal_value_rejects_whole_file_even_with_legal_entry
   （test_params_file.py:120-123）。
4. 参数名规则与区分大小写：键名须“首字符 ASCII 字母或下划线，后续
